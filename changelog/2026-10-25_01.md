## Why Care?

Every client so far either runs tools we deploy, or (humain-vc) a SaaS whose
vendor already ships the agent surface. Edviro is a third shape: they keep
HubSpot, and the agent layer on top is ours to build. If it works here, it
works for any client who arrives with a SaaS CRM.

## What's New?

- **A stack for Edviro** under `client-stacks/edviro/`, shaped like humain-vc:
  credentials and connector notes, no deploy config. Not committed, like every
  client stack.
- **A homebase page** at `lossless.at/edviro` (in the `hubs/lossless-at`
  submodule; not deployed yet). Its CRM card goes to HubSpot.
- **A plan** for the HubSpot interface and the MCP wrapper:
  `context-v/plans/Edviro-HubSpot-Interface-and-MCP-Wrapper.md`.

## The fact that changed the plan

HubSpot's remote MCP server (`mcp.hubspot.com`) went GA on 2026-04-13, on
every tier, with a native Claude connector. A wrapper that re-exposes
HubSpot's own CRUD would be one more thing to run for nothing. So the plan
starts Edviro on HubSpot's native connector, and builds the wrapper only for
the gaps: one-URL setup (HubSpot has no dynamic client registration),
queries past the 200-result and no-join limits, Edviro-specific tools, and
our audit and confirm layer on writes.

## What this deliberately does not include

No wrapper code, no Railway service, and no HubSpot credentials yet. Those
wait on Edviro's portal details and on what the native connector can't do.
