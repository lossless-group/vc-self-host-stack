## Why Care?

Anyone can write a spreadsheet showing that open-source tools are cheaper than
SaaS. The interesting question is whether a real fund can actually *run* on them
— whether the invitations send, the backups restore, the founder can open the
data room, and the partner can find the note six weeks later.

Four organizations now do. **The Water Foundation, Palmer AI, Reach University,
and The Lossless Group** are running production workloads on self-hosted
infrastructure they own: relationship data in Twenty, institutional knowledge in
Outline, diligence documents in Papermark, outbound scheduling in Postiz.

That's what this release marks. Not a feature — a threshold. The stack has users
who would notice if it broke.

## What's New?

- **Four client stacks in production**, each its own Railway project with its own
  database, storage bucket and private network. No shared tenancy anywhere.
- **Twenty running for all four**, each with an MCP connector so the CRM is
  reachable from Claude on desktop and mobile.
- **Outline on three**, each on a host the client owns
  (`wiki.<client>.lossless.at`) so share links survive being handed to someone
  outside the team.
- **Papermark** live as the first self-hosted data room; **Postiz** live as the
  first post planner.
- **Weekly `pg_dump` backups to R2**, per client, with the restore procedure
  drilled rather than assumed.
- **`lossless.at/<client>/<service>`** — one memorable address per tool,
  role-based so it outlives the vendor underneath it.
- **A 93-tool showcase** at the portal apex making the paradigm legible to people
  who haven't seen it.

**● live and reachable · ○ deployed but not yet usable**

Every filled circle is a real deployment with real records in it, not a demo
instance. Each client's secrets, database and object storage are separate; there
is no query anywhere in this architecture that could return one fund's pipeline
to another.

The one hollow circle is worth explaining, because it's the most useful kind of
gap. The Water Foundation's Postiz has been deployed and healthy since
2026-08-03 — and it cannot be logged into. Postiz derives its auth cookie domain
from `FRONTEND_URL`, and that instance is still pointed at
`*.up.railway.app`, which is a Public Suffix that browsers refuse to set cookies
against. Reach University's works because it sits on a real host
(`postiz.reach-edu.didi.sh`).

So it is running, it is costing money, and it is not a capability the client has.
It needs the same custom-domain cutover Reach got. **Deployed is not the same as
delivered**, and this release counts only what a client can actually open.

## What running it in production taught us

Shipping four stacks surfaced things no amount of local testing would have.

**The second user could never have logged in — on any of them.** Twenty's
`EMAIL_DRIVER` defaults to `LOGGER`, which renders every outgoing message into
the container's stdout and drops it. No error, no bounce, no failed job. The
first admin never touches that path, so all four instances passed their
walkthrough with it broken. It surfaced only when a second stakeholder at The
Water Foundation tried to accept an invitation that had been sitting in a Railway
log for four days.

The runbook was complicit: it listed SMTP under *"optional integrations… until a
client asks."* A client cannot ask for this — they don't know it's a setting,
they just experience a colleague who can't get in. That line is gone, replaced
with a section on why email is load-bearing and a second-user check in the
verification gate.

**Password reset dies by the same mechanism**, which is the more dangerous half.
It stays invisible until someone forgets a password, then it's a permanent
lockout with no recovery path. Nobody hit it. That was luck, not design.

**Some apps refuse to live under a subpath.** Outline requests `/static` and
`/api` as absolute paths, so proxying it under `/client/wiki/` resolves those
against the portal and breaks. Postiz derives its auth cookie domain from
`FRONTEND_URL`, and `*.up.railway.app` is a Public Suffix browsers reject
outright. Both needed real owned hosts. A redirect can point at a host; it cannot
hide one.

## The showcase

The portal apex was a title, one paragraph, and a suggestion to use the link your
operator sent you. It's now the argument for the paradigm: **93 open-source tools
across 32 categories**, each mapped to the proprietary product it replaces and
that vendor's real price.

The framing is deliberately not cost savings. It's that self-hosted open source
has no per-seat licence, so a small fund can give advisors, associates, interns
and outside counsel real access without the bill moving. Access stops being a
budget decision.

One number was made *smaller* on purpose. Summing the cheapest incumbent across
all 25 per-seat categories produced an accurate $709/seat/mo — and we cut it. No
fund buys 25 categories, and a figure that large reads as invented. What ships is
a named basket of nine vendors a partner can check against their own invoices.

Portfolio monitoring ships as an admitted gap: Visible.vc, Totem and Carta have
no open-source equivalent, the card says so, and it quotes Visible's $449/mo
rather than padding the category with a spreadsheet under a new name.

## Under the hood

The deployment pattern is one Railway project per client, four services per stack
(`twenty-server`, `twenty-worker`, `twenty-postgres`, `twenty-redis`) plus an S3
bucket, with `pg-dump-twenty` on a weekly cron writing to a per-client R2 bucket.

Three gotchas worth carrying forward, all of which cost real time:

```
PORT + NODE_PORT     Railway probes PORT; Twenty reads NODE_PORT. Set both or
                     the deploy fails its healthcheck at 04:52 every time.
TRUST_PROXY=1        Without it Express ignores X-Forwarded-Proto and OAuth
                     discovery advertises http:// — which breaks MCP client
                     registration with a misleading error.
CONFIG_EPOCH         `railway redeploy` silently reuses the PREVIOUS deployment
                     spec. Bump a throwaway variable to mint a fresh one.
```

Full procedure lives in `docs/twenty/setup.md`, which is now the authority — the
per-client `client-stacks/` directories are gitignored, so anything that must
survive a rebuild belongs in the shared doc.

## Known gaps

Named plainly, because a release record that only lists wins isn't a record.

- **Email is fixed on all four, but has not been proven by a live send.** SMTP is
  wired on both server and worker for every client and the config reads back
  correct on all eight services. What hasn't happened yet is an actual message
  leaving the box and arriving — config present and mail delivered are different
  claims, and only the second one counts.
- **Pricing on the showcase is largely unverified.** Figures carry
  `verified: false` and come from cited README research that is known to drift —
  Cal.com went closed-source in April 2026 and the table didn't notice for
  months.
- **The apex is `noindex`.** It names no clients and reveals nothing, but making
  the portal a public marketing surface is a decision, not a side effect.
- **What's deployed and what's routed have drifted.** `clients.ts` is the portal's
  routing table, not an inventory — The Water Foundation's Postiz is running but
  absent from it, so nobody at the client could reach it even once it has a
  working host. Reconciling the two is a standing chore, not a one-time fix; a
  tool a client can't reach from their homebase effectively doesn't exist.
- **Two dead services were removed during this release** — the `hub` service in
  palmer-ai and reach-edu, a stopgap per-client portal superseded by
  `lossless.at/<client>`. Both had been failing to build since 2026-08-09 (their
  Root Directory still pointed at a `hub/` folder that moved into a submodule),
  while their last successful containers quietly served stale copies on
  `palmer-ai.didi.sh` and `home.reach-edu.didi.sh`. A red build is loud; a
  frozen container answering 200 is not.
- **Their DNS records still exist.** Deleting a Railway service releases the
  hostname without removing the CNAME in the `didi.sh` zone, which leaves a
  dangling record pointing at an edge that no longer claims it — a subdomain
  takeover risk until the records are pulled.
- **One orphaned Postgres in reach-edu.** `temporal-postgres-<uuid>` has no
  deployments and nothing references it; the signature of a half-finished
  template provision. Harmless, but clutter.
- **One security pillar is an offer, not a capability.** SSO with MFA across every
  tool, admin surfaces on a private tailnet, and a unified audit log spanning all
  of them — buildable from parts already in the catalog, marked *Available on
  request*, not built.
